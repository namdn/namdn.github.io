Hồi ức · 2008–2009

Chúng tôi đã giải bài toán C10K thế nào

Từ mổ source Nginx, vặt lông Redis đến "phát minh lại" async/await.

Gần đây lướt mạng, thấy có ông anh nhắc lại bài toán C10K, tự nhiên bao nhiêu ký ức của cái thời 2008–2009 dội về.

Đó là cái thời web bùng nổ, và anh em làm backend hồi đó ai cũng đụng cùng một bức tường: Làm sao cho một con server cõng được mười nghìn connection cùng lúc? Anh Dan Kegel gọi nó là C10K problem.

Cách cũ bấy giờ là thread-per-connection (kiểu Apache prefork). Code đọc dễ, debug dễ, nhưng chết ở scale. Mười nghìn thread tức là bay ngay vài chục GB RAM chỉ để... ngồi đợi I/O. Cộng thêm việc context switch liên tục khiến OS scheduler ngộp thở. Resource cháy hết cho overhead chứ không cho work thật. Anh em tôi biết mình phải tìm một con đường khác.

Và đây là câu chuyện về cách chúng tôi đã giải nó, bằng cách chắp vá từ những người khổng lồ, và vô tình "chạm" vào tương lai của lập trình bất đồng bộ trước cả thế giới gần một thập kỷ.

1 Bài học vỡ lòng từ Nginx

Anh Nga ngố Igor Sysoev làm Nginx từ 2004 đi một con đường khác hẳn: event-driven, non-blocking I/O, một worker process cõng hàng vạn connection.

Mổ source Nginx ra, cái core của nó đơn giản đến mức choáng váng. Nó chỉ là một vòng lặp:

for (;;) {
    timer = find_next_timer();
    events = wait_for_io(timer);   // Chỗ duy nhất block
    for (each event in events) {
        handler(event);             // Không bao giờ block
    }
    process_timers();
}

Dòng wait_for_io() thì tùy hệ điều hành. Windows hồi đó chỉ có select() chạy O(n) theo số file descriptor (fd), còn Linux 2.6 đã có epoll chạy O(1), gồng được hàng trăm nghìn fd. Anh em quyết định ôm Linux là chuyện đương nhiên.

Có điều codebase Nginx to oành, đầy macro của anh Igor, viết để chạy production chứ không phải để học. Đọc mãi không vô. May thay, đầu năm 2009, một "vị cứu tinh" khác xuất hiện.

2 Mổ source Redis để học Event Loop

Tháng 2/2009, anh Ý đảo Sicilia — antirez — công bố Redis. Một thread, một event loop, mà throughput khủng khiếp.

Bí mật nằm gọn trong vài file: ae.h cho interface, ae.c cho core (chỉ tầm 400 dòng), rồi ae_epoll.c / ae_kqueue.c / ae_select.c cho từng OS. Tên ae viết tắt của "A simple Event-driven programming library". Cả file chính tôi ngồi đọc một buổi sáng là xong.

API public gọn lỏn vài hàm: tạo/hủy event loop, đăng ký file event cho một fd, time event, aeMain để khởi động vòng lặp. Phần platform-specific giấu sạch sau wrapper thống nhất.

Anh em tôi bê nguyên ae về xài luôn, không động dao kéo gì vào bên trong. Cái chúng tôi mang lên tầng framework ứng dụng là kiến trúc — cách tách public API khỏi platform-specific code.

Event-driven tự nhiên "dễ như ăn kẹo"

Có cái event loop từ Redis trong tay, viết event-driven nhàn tênh. Có fd ready? Đăng ký callback. Cần timer? Đẩy vào time event queue. Engine ae lo nốt. Cái HTTP server tự nhiên rơi xuống: accept-loop trên port 80, parse request ra, tra routing table, gọi handler đã đăng ký.

@http.get("/users/*")
def get_user(httpContext):
    user_id = httpContext.path.split("/")[-1]
    # ... build response ...

Pattern đó áp dụng cho mọi protocol. Hồi anh em làm game backend, chỉ cần thay parser và dispatcher, đăng ký handler theo opcode thay vì HTTP path:

@socket_event(opcode=0x0A)        # MOVE
def on_move(player, dx, dy):
    player.x += dx; player.y += dy
    broadcast_to_room(player.room_id, MoveEvent(player.id, dx, dy))

Engine không đổi một dòng. Cùng một backend vừa cõng REST API cho team product, vừa cõng game realtime cho team game. Đây mới đúng là "platform" — một cái nền cho nhiều sản phẩm khác nhau đứng lên, chứ không chỉ là một con server giải C10K.

3 Nửa kia của tảng băng: Nỗi đau mang tên Callback Hell

Đến đây, Redis giải đẹp phần connection đi vào. Còn phần I/O đi ra thì Redis bó tay.

Vì khi handler chạy, nghiệp vụ thật mới bắt đầu: query MySQL lấy user, gọi HTTP service nội bộ lấy profile, ghi log, v.v. Mọi bước I/O đó phải non-blocking, vì chỉ cần một query MySQL chậm là đóng băng cả 9.999 connection còn lại đang share cái event loop kia.

Hồi 2008–2009, để viết code non-blocking, anh em chỉ có hai lựa chọn, và cả hai đều... "khó chịu thí mịa".

  • Thread-per-connection: Dễ đọc, dễ try/catch, nhưng chết với 10K connection vì tốn RAM và overhead.
  • Event-driven với callback: Cách mà Node.js (vừa ra mắt 2009) đang đẩy lên trend.

Lúc Node.js mới ra, anh em cũng phát cuồng với cảm giác hiện đại, "đây mới là tương lai". Nhưng đến lúc viết app thật, lồng 5–7 tầng cho một flow nghiệp vụ phức tạp, mới thấy tận cùng của nỗi đau:

def handle_request(conn):
    def on_read(req):
        def on_user(user):
            def on_profile(profile):
                conn.write(render(user, profile))
            http.get_async(f"http://profile-svc/{user.id}", on_profile)
        db.query_async("SELECT * FROM users WHERE id=?", req.user_id, on_user)
    conn.read_async(on_read)

Đây chính là thứ mà mãi sau này cộng đồng mới đặt tên: Callback Hell. Bốn cấp indent cho một flow tầm thường. Try/catch vô nghĩa vì exception ném từ callback có lan ngược lên được đâu. Stack trace thì cụt ngủn ở event loop.

Workaround của anh em hồi đó là... tống hết logic xuống Stored Procedure của MySQL. Một cú CALL sp_handle_order(...) thay cho 5 callback lồng nhau. Sạch trên giấy, nhưng đau khổ trong dài hạn:

  • Logic bị xé đôi giữa Application và SQL.
  • Deploy đồng bộ là một cơn ác mộng.
  • Code không thể test được (phải dựng MySQL thật, seed data thật).
  • Đau nhất: SQL không có đủ hàm, anh em phải chế hẳn MySQL plugin viết bằng C, compile thành shared library load vào MySQL server.

Đến lúc phải hack MySQL bằng C plugin chỉ để vá một mô hình lập trình sai từ đầu, chúng tôi biết mình đã đi quá xa rồi.

4 Khoảnh khắc "Eureka" với yield

Một hôm lang thang đọc tài liệu Python 2.5/2.6, tôi vớ phải một feature thực ra đã có từ PEP 255 (năm 2001): generator với keyword yield.

Python đẻ ra yield vốn dĩ không phải để giải quyết bài toán concurrency. Nó sinh ra để viết iterator cho gọn (thay vì phải đẻ ra một class với __iter__ / __next__):

def fibonacci():
    a, b = 0, 1
    while True:
        yield a
        a, b = b, a + b

Đến PEP 342 (2005), Python thêm .send(value) — caller truyền value ngược vào generator, và value đó sẽ thành kết quả của biểu thức yield đã ngủ từ lần trước. Hồi đó người ta vẫn chỉ coi đây là "iterator nâng cao".

Cái làm nên chuyện của yield là một thuộc tính cực kỳ ăn tiền: Một hàm có thể dừng giữa chừng, trả quyền điều khiển ra ngoài, rồi được caller "đánh thức" để chạy tiếp từ chính chỗ vừa dừng — với toàn bộ biến local vẫn nguyên xi.

Hơn nữa, yield là một biểu thức hai chiều: đẩy giá trị ra, và nhận giá trị vào (qua .send()). Nhìn cái flow này là hiểu ngay:

def gen():
    x = yield 10        # khi resume, send-value chui vào đây thành x
    y = yield 20        # lần resume kế tiếp, send-value chui vào đây thành y
    return x + y

Ba điểm cốt lõi lộ ra:

  • g.send(value) đẩy value vào chỗ yield đã ngủ từ lần trước.
  • Generator chạy tiếp đến yield kế tiếp, đẩy vế phải của nó ra.
  • Cái vế phải ấy chính là return value của hàm send.

Có cơ chế này thì một hàm Runner hoàn toàn có thể làm được việc: ném kết quả I/O vừa xong vào generator (qua send), nhận việc kế tiếp ra, rồi lặp lại. Và ai sẽ gọi .send() để đánh thức generator khi I/O xong? Câu trả lời đã nằm sẵn trên bàn: chính cái event loop ae.c chôm từ Redis.

5 Ráp lại thành Coroutine Model (async/await đồ đá)

Ý tưởng gom lại cực gọn: Khi code application cần I/O, nó không gọi callback nữa. Nó yield ra một object mô tả việc cần làm.

Bên ngoài sẽ có một hàm run đóng vai trò "lái" generator: nhận object về, gọi schedule() của nó, lúc nào I/O xong thì lấy kết quả ném ngược vào generator. Lặp lại cho đến khi xong việc (StopIteration).

Anh em tôi gọi mỗi hàm như vậy là một task (mãi sau này từ học thuật coroutine mới thành chuẩn chung). Cái ghép nối tất cả lại — generator của user, event loop Redis, mấy cái YieldReturn — là một cái decorator @task đơn giản. Decorate một hàm có yield bằng @task thì khi gọi, hàm đó không chạy ngay mà trả về một TaskReturn (chính là một YieldReturn bọc generator).

Nhờ vậy cả hai use case cùng work trên một cơ chế:

  • Listener gọi handle_request(conn) lấy TaskReturn đẩy vào event loop để chạy.
  • Trong code, yield other_task() chỉ là yield một YieldReturn bình thường — framework tự drive sub-task đến hết rồi trả kết quả về.

Một decorator, hai use case, không có syntax riêng cho sub-task call. Flow callback hell nát bét ở trên, giờ viết lại đẹp như mơ:

@task
def handle_request(conn):
    req     = yield conn.read()
    user    = yield db.query("SELECT * FROM users WHERE id=?", req.user_id)
    profile = yield http.get(f"http://profile-svc/{user.id}")
    yield log.write(f"served {user.id}")
    yield conn.write(render(user, profile))

Cùng logic, cùng performance, chạy trên cùng cái event loop một thread cõng hàng vạn connection. Khác mỗi việc rải mấy chữ yield vào đúng chỗ. Code tuần tự, bắt try/catch ngon lành.

Toàn bộ pattern này được chúng tôi gói gọn trong vài chục dòng code. Mỗi loại I/O là một subclass nhỏ của YieldReturn, tự override hàm schedule():

import functools

class YieldReturn:
    def schedule(self):
        raise NotImplementedError

class MySqlReturn(YieldReturn):
    def __init__(self, sql): self.sql = sql
    def schedule(self):
        # Bridging giữa callback và event loop giấu hết vào đây
        return loop.await_mysql(self.sql)

class db:
    @staticmethod
    def query(sql): return MySqlReturn(sql)

def run(gen):
    """Drive generator đến khi kết thúc, trả về final value."""
    value = None
    while True:
        try:
            yr = gen.send(value)
        except StopIteration as stop:
            return getattr(stop, 'value', None)
        value = yr.schedule()

class TaskReturn(YieldReturn):
    """Bọc một generator. Triết lý: yield một TaskReturn = chạy nó đến hết."""
    def __init__(self, gen): self.gen = gen
    def schedule(self):
        return run(self.gen)

def task(genfunc):
    @functools.wraps(genfunc)
    def wrapper(*args, **kwargs):
        return TaskReturn(genfunc(*args, **kwargs))
    return wrapper

Mental model lúc này cực kỳ nhất quán: Gọi hàm để tạo task, yield để chạy và lấy kết quả. Cần chạy song song? Thêm YieldParallel(*tasks) (đúng cái mà sau này JS gọi là Promise.all, Python gọi là asyncio.gather). Cần timeout hay fallback? Đẻ ra YieldFirst(*tasks) (giống Promise.race).

Mỗi class phụ trợ như vậy chưa tới 30 dòng code, không hề động chạm gì tới core. Xong cái core này, mọi thứ khác (Connection pooling, Rate limiting, Circuit breaker, Retry with backoff...) đều tự động vào guồng. Anh em dev ứng dụng cứ thế mà múa yield, không cần biết bên dưới đang direct hay qua pool.

6 Nhìn lại: Bài học đắt giá về sự chia sẻ

Cái framework "nhà làm" này được gói trong 3 layer xếp chồng:

  • Event loop bê nguyên từ Redis ae ở đáy.
  • YieldReturn + run + subclass ở giữa.
  • Application code với hàm @task và vài chữ yield ở tầng trên cùng.

Hồi đó, anh em trong team ai cũng biết là mình vừa làm được một thứ rất xịn. Nhưng cũng vì thấy nó xịn quá, nên giấu nhẹm đi. Giấu như mèo giấu cứt. Không public, không viết blog, không open source.

Giờ ngồi nhìn lại, có lẽ đó là cái sai lớn nhất của cả hành trình.

Vài năm sau, cả ngành công nghiệp phần mềm tự đi đến đúng cái mô hình ấy bằng những con đường vòng:

  • Tornado (2009) đi lối yield-based coroutine. (Hồi Tornado ra cái @coroutine, anh em trong team còn đùa nhau là thằng này ăn cắp của anh Nam kìa.)
  • Python ra PEP 380 (2012) thêm yield from.
  • Python ra PEP 492 (2015) đưa async/await làm keyword chính thức — mà bản chất nó chính là syntactic sugar cho đúng cái cơ chế mà anh em tôi đã cặm cụi tự build bằng tay từ 6 năm trước.
  • Rồi JavaScript theo sau với ES2017 (async/await). C# có từ bản 5.0. Rust ổn định vào 2019.
